BreakBridge – The live break scheduling and staffing decision tool for childcare operations.

This project is a migration from an existing React/Vite prototype that already contains meaningful product behavior, UI patterns, and business logic. Treat the existing prototype as source material for migration, not as the target architecture.

The goal is to evolve BreakBridge into a production-ready, multi-tenant SaaS platform.

Tech stack (non-negotiable):
Frontend: React (Vite)
Backend: NestJS (TypeScript)
Database: PostgreSQL
ORM: Prisma
Auth / realtime / storage: Supabase
Jobs / queues: BullMQ + Redis
Deployment: Render

Initial goal:
Do NOT attempt to complete the full SaaS platform in one pass.

The first objective is to:
• create a clean production-grade monorepo structure
• scaffold backend services and database schema
• establish API boundaries
• define system architecture
• prepare for controlled migration of the existing MVP

---

Architecture requirements:

Design for multi-tenancy:
Organization → Location → Classroom → Staff

The backend must be modular and scalable, with clear separation of concerns.

Required backend modules:

• auth (Supabase integration)
• organizations
• locations
• classrooms
• staff
• attendance (snapshot ingestion)
• breaks (break plan generation)
• coverage (coverage assignments)
• rules (rules engine)
• audit (logging + traceability)
• integrations (external systems like Tadpoles)
• exports (break plan output + automation handoff)

---

Core entities:

• Organization
• Location
• Classroom
• Staff
• AttendanceSnapshot
• BreakPlan
• BreakAssignment
• CoverageAssignment
• RuleConfig
• AuditEvent

Supporting entities (if needed):

• UserLocationAccess
• AttendanceSnapshotEntry
• ExclusionRule
• ShiftHint
• ExportArtifact

---

Frontend requirements:

Build a polished operational dashboard shell that includes:

• organization / location context
• classroom tiles with ratio awareness
• staffing legend (Green / Fragile / Maxed)
• break plan summary
• attendance import screen
• coverage schedule screen
• rule configuration placeholder
• audit log placeholder
• admin navigation

The frontend must consume backend APIs.

The frontend must NOT contain the core break rules engine.

Preserve these product concepts from the prototype:

• staffing board behavior
• ratio-aware room status
• paste/import workflow
• auto-propose break logic (conceptually)
• coverage schedule visibility
• break plan summary
• manual overrides (out / exclude / adjust)

---

Backend requirements:

Implement a Rules Engine service responsible for:

• ratio evaluation
• break eligibility determination
• coverage assignment logic
• conflict detection

Add a first-pass Tadpoles integration contract:

• attendance snapshot import endpoint
• break plan export endpoint
• future UIPath automation compatibility

Model these as backend workflows, not frontend hacks.

---

Important constraints:

• Do NOT move business logic into the frontend
• Do NOT collapse multi-tenant relationships
• Do NOT skip Swagger or API documentation
• Do NOT expose real employee names or real childcare data
• Use fictional sample data only
• Do NOT generate large amounts of code before analysis

---

Deliverables:

1. Monorepo structure (frontend + backend)
2. NestJS backend scaffold with modules
3. Prisma schema (initial version)
4. Supabase integration scaffold
5. REST API structure (Swagger enabled)
6. Basic frontend dashboard shell
7. Example API flow (attendance → break plan)
8. README with architecture explanation
9. Migration plan (prototype → architecture)
10. Tadpoles import/export contract (initial version)
