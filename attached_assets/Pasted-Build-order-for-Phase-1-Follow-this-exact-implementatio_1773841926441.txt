Build order for Phase 1:

Follow this exact implementation order. Do not skip ahead to advanced features before the foundation is in place.

PHASE 1A — MONOREPO FOUNDATION
1. Create the monorepo structure exactly as requested:
- apps/web
- apps/api
- packages/shared
- packages/config

2. Set up workspace-level tooling:
- TypeScript base config
- shared lint/format config if useful
- environment variable structure
- root scripts for dev/build/test where appropriate

3. Keep this a modular monolith.
Do not create microservices.

PHASE 1B — BACKEND FOUNDATION FIRST
4. Create the NestJS app in apps/api with the required module structure:
- auth
- organizations
- locations
- users
- roles
- classrooms
- staff
- attendance-imports
- break-plans
- coverage-assignments
- rule-engine
- audit-events
- integrations
- jobs
- admin

5. Set up Prisma with PostgreSQL.
Use Prisma, not Drizzle.

6. Create the initial Prisma schema using the domain language from the master prompt:
- Organization
- Location
- User
- Role
- Classroom
- StaffMember
- AttendanceSnapshot
- BreakPlan
- BreakAssignment
- CoverageAssignment
- RuleSet
- AuditEvent
- IntegrationRun
- ImportJob
- ExportJob

7. Build the schema for multi-tenancy through Organization and Location relationships from day one.
One Organization has many Locations.
Users belong to an Organization and may be scoped to one or more Locations.

8. Add migrations and seed scripts with fake childcare demo data only.
No real employee names or real customer data.

PHASE 1C — AUTH / SECURITY FOUNDATION
9. Add Supabase-compatible auth scaffolding.
Keep it minimal but real:
- login/session verification foundation
- user identity mapping
- organization scoping
- role-aware authorization scaffolding

10. Implement role scaffolding for:
- Platform Admin
- Organization Admin
- Location Admin
- Supervisor / Scheduler
- Read-Only Viewer

PHASE 1D — API CREDIBILITY
11. Add Swagger/OpenAPI support for the NestJS backend.
Swagger should expose the initial DTO-based API shape.

12. Add DTO validation and clear controller/service boundaries.

13. Add audit-event hooks for important actions such as:
- creating or updating staff
- creating snapshots
- generating break plans
- editing coverage assignments
- changing rules

PHASE 1E — FRONTEND SHELL
14. Create the React + Vite + TypeScript frontend in apps/web.

15. Build only the operational shell first:
- organization/location context
- admin navigation
- classroom tiles
- staffing legend
- break plan summary
- import snapshot screen
- rule configuration placeholder
- audit log placeholder

16. Do not migrate the full prototype UI yet.
Do not dump the 4,700+ line App.jsx into the new structure.

PHASE 1F — SHARED CONTRACTS
17. Create packages/shared for shared types/contracts used across frontend and backend.
Keep shared contracts clean and explicit.

PHASE 1G — FIRST REAL FEATURE MIGRATION
18. Migrate in this order:

A. Classroom / board read model
- backend endpoints to return location, classrooms, room ratios, room capacities, and staffing board data

B. Staff management
- staff CRUD
- exclusions
- default room assignments
- shift metadata
- no-break and force-30 flags

C. Snapshot import boundary
- move Tadpoles import parsing to the backend
- frontend only sends pasted raw text
- backend returns structured parsed results

D. Break proposal engine
- move auto-propose logic into backend services
- frontend becomes a consumer of proposal results

E. Coverage assignments
- backend-generated coverage records
- frontend shows/editable schedule UI

F. Availability events
- persistent database-backed availability and planned absence records

PHASE 1H — WHAT TO POSTPONE
19. Postpone these until the above is complete:
- advanced realtime features
- production BullMQ workflows
- export automation
- full integrations
- highly polished admin UX
- advanced analytics
- multi-environment deployment complexity

IMPORTANT IMPLEMENTATION RULES
- Do not change the selected stack.
- Do not use Express instead of NestJS.
- Do not use Drizzle instead of Prisma.
- Do not place business rules in the frontend.
- Do not flatten Organization and Location into one level.
- Do not use real employee names in seed data.
- Do not migrate everything at once.
- First create a clean backend and frontend shell, then migrate behavior in small controlled slices.

1. Monorepo folder structure

4. Auth/role scaffolding draft

6. Seed strategy summary
